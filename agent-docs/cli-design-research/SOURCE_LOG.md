# CLI Design Source Log

This log records sources reviewed for the CLI design guide. The final guide
should cite only sources that materially support its conclusions.

## Source Conclusions

1. The strongest cross-source agreement is that a CLI is both a human interface
   and an automation contract. Good designs must serve both without letting one
   silently corrupt the other.
2. Structured output should be explicit and stable. Human output can be richer,
   but scripts need documented formats such as JSON, JSON lines, or stable
   plain records.
3. Interactivity must be TTY-aware and escapable. Prompts are useful for humans
   but dangerous in CI unless there is an explicit `--no-input`,
   `--yes`/`--force`, saved plan, or equivalent automation path.
4. Dangerous operations need preview, confirmation, naming, and rollback/status
   surfaces proportional to the severity of the action.
5. Discoverability is not optional. `--help`, examples, suggestions,
   completions, and actionable errors are the CLI equivalent of visible UI.
6. Configuration should have explicit precedence, should distinguish
   invocation-specific flags from environment and durable config, and should
   avoid leaking secrets through flags or logs.
7. The best case studies are instructive, not perfect. Git is powerful and
   durable but demonstrates compatibility debt; `gcloud` is expressive but
   complex; Terraform is safety-oriented but domain-heavy; `rg`/`fd` show the
   power and risk of opinionated defaults.
